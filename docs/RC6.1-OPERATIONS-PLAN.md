## Outcome A — every gate met

Keep evidence of all gates: developer review; clean locked installs; complete unit and mock browser suites; production build showing RC6.1; real rules compilation and full rules suite with zero failed or skipped tests, including RC6-MAX 12-line transactions and maintenance-freeze tests; real Auth/Firestore emulator browser workflows; a tested backup/restore; real-data preflight COMPLETE/READY using verified exports; owner decisions below; confirmation of the previously reported GitHub token revocation. See RC6.1-DEVELOPER-REVIEW-GUIDE.md for commands and acceptance criteria. Do not treat mocked tests or static rules checks as real Firebase verification.

Before any deployment, the developer confirms the intended project and records the known live build. Preserve the tested backup and a reviewed recovery plan. During the maintenance window:

1. Apply the reviewed freeze configuration (`firebase.freeze.json`, `rules/maintenance-freeze.rules`) through the developer's normal authorised release procedure. Verify an ordinary client write is denied. Keep maintenance active throughout export, assessment and recovery. Read-only REST calls made with an administrative access token do not prove the freeze; the developer must verify it independently.
2. Export the required data using the GET-only exporter. A local rehearsal uses `node tools/export-readonly.mjs --project naisi-rules-test --host http://127.0.0.1:8080 --out <new-empty-directory>`. A remote export is a separate developer-authorised action and requires `--host https://firestore.googleapis.com --allow-remote --confirm-project <same-project-id>` in addition to `--project <same-project-id>`; supply the access token through `FIRESTORE_ACCESS_TOKEN` using a secure environment mechanism. Never put its value in a command, file, report or screenshot. Do not use the emulator project id for a real project. This preparation has not performed remote exports.
3. The exporter writes orders.json, invoices.json, invoiceNumbers.json, orderCancellations.json, stockMovements.json, customers.json, products.json, scheduleChanges.json, counter.json and scheduleHistory.json, each an array with document ids, plus manifest.json. An empty singleton array means that document is absent. Only use a completed manifest and all its files together. REST pagination is not an atomic cross-collection snapshot; verify writes stayed frozen and verify that the chosen project and collection scope are correct. Counts and hashes prove file integrity, not that a server omitted no documents.
4. In the export directory, run `node <source>/tools/reconcile.mjs orders.json invoices.json --manifest manifest.json`. Require `completeness: COMPLETE` and `dataReadiness: READY`; review every finding and maxLinesFound. Run `node <source>/tools/migrate-rc3.mjs --files . --manifest manifest.json` as an additional DRY RUN. A CLEAN migration assessment does not cover stock-ledger, customer or schedule reconciliation. The catalogue is required: manifest mode supplies it; the legacy explicit option is `--products products.json`. These assessment commands never authorise deployment or a live migration. A manifest mismatch/missing file must return INCOMPLETE with exit 3; fix the export, not its manifest.
5. Record the verified freeze time with an explicit zone, for example `2026-10-19T05:30:00+02:00`. Run `node <source>/tools/stuck-invoicing.mjs orders.json invoices.json invoiceNumbers.json --manifest manifest.json --frozen-at <actual-ISO-time-with-zone>`. The manifest supplies the real export start/end times; the tool rejects exports begun before the stated freeze. Optional `--exported-at` must agree with the manifest end time. Any timestamp after export or after freeze plus `FREEZE_TIMESTAMP_TOLERANCE_MS=1000` prevents a confirmed result. This one-second precision allowance is not a grace period for live writes. The tool checks consistency of stated times and available timestamps; it cannot verify the freeze itself.
6. Recovery remains manual and read-only. SAFE_TO_RELEASE is narrow: all checks agree, with no plausible unclaimed invoice. Similar customer identity/name or any product overlap can require review even with different totals/items. Earlier reliable invoice dates exclude candidates; absent dates cannot exclude them. Expect conservative false positives. NEEDS_REVIEW or INPUTS_INCOMPLETE means stop and investigate, not retry invoicing. For SAFE_TO_RELEASE follow the printed developer checks, retain evidence, then re-export after the intentional maintenance edit with a fresh freeze checkpoint while maintenance remains active. For ALREADY_INVOICED follow the procedure below. Resolve every stuck order before unfreezing.
7. After approval of the frozen data and release candidate, the developer deploys indexes and waits for completion, builds from the reviewed source, checks `dist/build-id.txt` equals RC6.1, deploys hosting, then restores the reviewed application rules whose hash matches HASHES.txt. Confirm the live page shows Build RC6.1. Deployment credentials and project selection are the developer's responsibility; no deployment command has been executed here.
8. Close/reopen or hard-refresh each participating device; verify Build RC6.1. Begin with one rep and one manager, developer available. Run the supervised pilot below before wider use.

## ALREADY_INVOICED: complete the existing order

This completes the relationship to an existing invoice. Never return the order to Approved and never issue a new invoice for this repair.

1. Keep writes frozen and verify project, backup, operator and fresh manifest-backed exports. Preserve the old order fields. Ensure no other operator is repairing the same records.
2. Inspect the order and identified invoice: customer, actual sale, line quantities/prices, totals and invoice number must agree. Search orders, invoices and number registry for conflicts and duplicates. Exactly one invoice must belong to this sale. Stop for a mismatch or plausible additional orphan and resolve with the owner/developer.
3. Verify `invoiceNumbers/<invoiceNo>.invoiceId` equals that invoice's id and that the invoice's number agrees. Check `counters/naisiInvoice.prefix` and `.counter`: counter is the NEXT suffix to issue and must be greater than every already-issued suffix for that prefix and the current Malawi calendar year. The number builder uses the Malawi year at issue time; the counter document has no year field. Never decrement it; missing/conflicting registry or counter repairs need separate owner/developer review. Do not create a new invoice to repair a link.
4. Edit only the existing order: set `status = "Invoiced"`, `invoiceId` and `invoiceNo` to the verified invoice; clear `invoicingAttempt` and `invoicingLeaseStartedAt`; set `updatedAt` to the actual repair time. Do not change invoice totals, product quantities or stock-movement rows.
5. Retain an audit note with operator identity/uid, UTC time, reason, order id, verified invoice id/number, previous status and lock fields, and export manifest/hash identifiers. Keep it with the signed recovery evidence. Any additional on-record audit note must use the developer's reviewed administrative procedure. The classifier writes nothing.
6. Because the intentional repair changes updatedAt after the original freeze, record a fresh consistency checkpoint after repair while maintenance remains active. Export again to a new directory. Re-run the classifier: the completed order must no longer be listed. Run reconcile; verify order/invoice/registry/counter links, unchanged invoice count and unchanged stock balances/ledger counts. A developer approves ending maintenance only after these checks agree.

## Supervised pilot and stop conditions

Rep: sign in, see today's route, log a no-order visit, submit a catalogue order once. Manager: inspect equal-price, changed-price and missing-catalogue-price lines; changed prices require explicit acknowledgement and retain submitted prices. Verify the acknowledgement in the stock ledger, including actor, server time, affected lines and order/catalogue prices. Approve once, verify stock deducted once; invoice once; complete delivery/payment workflows; validate expense entry. Re-export and reconcile. An order with agreed discounts must remain approvable after acknowledgement; current policy warns rather than imposing catalogue prices.

Freeze and stop for duplicated/missing invoices, stock mismatch, permission denial on a valid action, an order stuck in Invoicing, unexplained writes, inconsistent exports or a stale build. Preserve evidence and use the tested backup/recovery procedure. Fix forward by default; using any older release requires separate owner/developer review of known defects and data compatibility. Never assume an earlier RC is a safe rollback.

## Outcome B — any required check or approval not met

**Do not deploy RC6.1.** The developer and owner choose either the currently live build after assessing its suitability, or manual capture. A restricted workflow is not a fix for a security defect; do not use the live build if the developer considers it unsuitable.

For an approved existing-live workflow, identify its exact build and support contact; use scheduled visits and catalogue order submission only as approved by the developer. Record every submitted order number separately. On a hang, check whether the order already exists before any retry; ask the manager. Never retry an order stuck in Invoicing. Manager reconciles the daily sheet with orders, invoices and stock.

Manual capture uses separate Visits and Orders sheets. Assign every order a unique `MAN-<initials>-<yyyymmdd>-<nn>` identifier; capture customer, date/time, products, quantities, agreed prices and total. Capture visit outcomes and reasons for no order. Keep originals and give the manager a copy. Manual orders do not reserve app stock: the manager maintains the allocation list. Do not issue app invoices from unentered manual records. After an approved deployment, search for existing customer/date records, enter each MAN order once with its identifier, tick it off in a reconciliation register, and invoice only its one app order.
